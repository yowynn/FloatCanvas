# UI 与绘制分离调查（2026-10-25）

基线：`4c3259f`，三期画布 Esc 和预设角标修改不涉及预览管线。调查未修改产品渲染策略。结论是：重绘慢时，工作线程确实让 UI 能继续处理输入；轻量、缓存命中和高分辨率场景则付出了明显的像素复制、再次提交及排队成本。不能把“移到另一个线程”视为所有场景的优化。

## 实测方法与边界

`FloatCanvas.AppTests --phase3-preview-investigation` 仅运行离屏 Skia/WPF dispatcher，不创建窗口、不采集桌面、不注入输入。比较原同步路径使用的 `OverlaySceneCache.DrawOnClearedRasterTarget` 与实际 `CanvasPreviewPump`／`CanvasPreviewRenderer`：保持同样的预热、场景、选中末层、缓存前缀、事务和 CPU 目标，测量当前帧从请求到 UI 离屏复制完成的时间。每组预热 5 次，轻量组 40–60 个样本；路径组 12 个样本。运行两轮。后者不包含 `UpdateLayeredWindowIndirect`、DWM 或物理显示延迟；前者也不是旧版本完整应用的端到端时间。

`--phase3-preview-routing-investigation` 创建两个完全位于桌面外的自有 HWND，经过真实 `DesktopSession.RenderFrame`、`PresentCanvasPreview` 和原生提交。独立测试 profile，无编辑输入租约、无快捷键、无桌面捕获；第二次运行观察到自有进程前台事件为 0，前台 HWND 也保持不变。第一次的“前台 HWND 不变”断言失败，未计为通过；该条件会受用户正常切换窗口影响，现记录前台是否变化，并独立检查测试进程是否取得前台。

机器：本地 Windows x64、Release 构建；时间是此次机器负载下的样本，不是通用性能保证。原始 JSON 和日志保存在本地三期 artifacts，不纳入源码。

## 轻量与缓存命中场景

下表为两轮中位数范围，单位 ms。各阶段的中位数不能直接相加，也不能用 P95 相减归因。

| 场景 | 原同步缓存栅格 | UI 快照 | 工作线程渲染及不可变像素复制 | UI 再复制 | 请求至离屏复制完成 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1280×720，1 个矩形 | 0.34–0.38 | 0.016–0.023 | 0.80–0.95 | 0.46–0.56 | 1.52–1.80 |
| 3840×2160，1 个矩形 | 5.06–5.21 | 0.040–0.043 | 10.26–10.34 | 6.46–6.50 | 17.94–18.02 |
| 1280×720，100 个矩形 | 0.59–0.62 | 0.071–0.076 | 1.03–1.09 | 0.46–0.49 | 1.74–1.88 |
| 1280×720，3000 条路径，静态前缀缓存命中 | 0.79–0.82 | 0.56–0.64 | 1.51–1.59 | 0.58 | 3.05–3.24 |

4K 单矩形的异步离屏 P95 为 19.87–19.90 ms。此时场景几何很简单，主要代价随整屏像素数增长；不能归因于复杂几何或 GPU 滤镜。3000 层组的快照每次在 UI 分配约 2.71 MB，少量样本出现 9.77–9.80 ms 快照尖峰；12 个样本不足以把这个尾部百分位推广到实际会话。路径点使用 `PointCollection.Snapshot()` 的写时复制，不能把这笔分配解释为每帧复制所有 144000 点。

现有 `--phase2-render-only` 慢帧回归也重新运行：3000 层、144000 点、不透明度完整重绘，同步栅格 424.05 ms、UI 快照请求 1.12 ms、工作线程 390.06 ms，期间收到 25 次输入优先级心跳。这证明慢帧隔离仍有效；它不抵消轻量场景的额外成本。

## 已确认的问题与机制

1. **完整像素经过额外复制。** `PreviewRasterizer.Render` 将复用 DIB 复制为独立 `SKImage`；UI 的 `Draw` 再把图像画回输出 DIB，随后还有系统提交。4K BGRA 两次复制涉及至少 66.36 MB 像素／完成帧；单个缓冲区约 33.18 MB。UI 复制本身约 6.5 ms，说明 UI 仍承担随屏幕尺寸增长的工作。数据脱离线程是必要的，当前的完整复制方式才是需要优化的部分。
2. **每次编辑提交两遍。** 生产路由实测输出屏数为 `[2,2]`：`RenderFrame` 先提交旧预览与最新控制柄，工作完成后 `PresentCanvasPreview` 再提交新预览。测量是实际原生提交次数，不是推算。交互控制柄即时更新有价值，但静态／无需变化的像素也重复提交。
3. **局部／单屏脏区在异步完成时丢失。** 单屏更新实测 `[1,2]`：首遍遵守指定屏，完成回调无条件 `_host.Render()` 刷新全部输出。工作快照的 `Outputs` 也始终包含所有屏幕。原有动画／实时特效脏区优化只约束了第一遍。
4. **完成帧排在输入和 Render 工作之后。** `CanvasPreviewPump.Work` 以 `DispatcherPriority.Background` 投递完成回调。在有界顺序探针中，200 个排队 Input 操作全部先执行，完成帧才发布。这证明繁忙输入可能延后显示更新；该探针没有证明真实用户输入会造成无限饥饿，也不是实际延迟数字。
5. **已过时的完成结果仍先发布。** 同一上下文里，工作线程处理值 1 时 UI 已请求值 2，确定性探针仍依次发布 `[1,2]`。`CanvasPreviewFrame` 不携带 scene revision／transaction，展示侧仅校验画布、监视器等上下文。画布切换、隐藏上下文已有保护，但同一画布的新状态不会使旧结果失效。最新控制柄可能与旧场景不同步；具体可见时长尚需桌面交互验证。
6. **场景快照和部分资源工作仍在 UI。** `CaptureCanvasPreview` 遍历克隆所有元素及引用资源；场景越大，其分配越大。动画探测和调度仍使用 UI 的独立 `SceneRenderer`，工作线程又持有自己的解码与缓存；是否构成特定素材的明显停顿尚未测量。不能宣称整个绘制相关计算都已移出 UI。

队列没有无界积压：工作忙时只保留 pending 标记，完成后捕获最新状态；关闭不等待慢帧；图像不可变、桌面背景引用保留、CPU/GPU 失败回退和最终值收敛的现有回归通过。上述有效部分应保留。

## 修复顺序建议

先修复可独立验证的重复提交和脏区丢失，再给帧增加明确的输入版本与展示策略，权衡最新控制柄与场景一致性。像素交换应以减少整屏复制和复用受控缓冲为目标，不能让工作线程与 UI 同时读写同一 DIB。快场景是否直接渲染必须由受限预算和场景／历史耗时决定，避免把不可预测的慢帧重新放回 UI；不建议在本次调查里直接切回单线程或堆叠更多线程。

下一阶段应测实际 4K／多屏画笔与对象拖动、UI 输入间隔、像素提交次数、内存分配及最终值一致性，再决定策略。此文为调查交付，不代表这些优化已经实现，也不将用户尚未写完的性能描述补成某个具体复现场景。

## 系统截图是独立问题

增强画布通过 `CreateWindowInBand(...,16)` 创建；普通 topmost 排序回归不能代表系统截图蒙层的真实层级。失去焦点的生产回调会立即隐藏工具条，这是另一个独立时序。Notion 原图已通过后台 API 取得并实际查看：蓝色画布覆盖了截图选区边框及截图工具按钮，工具条局部可见。后续窗口事件观测已确认系统截图位于 band 1，增强输入委托还可能让全局前台留在原应用；不能将此问题直接归因于预览线程。专门修复及验证边界见 [系统截图交接](System-Screenshot-Handoff.md)。
