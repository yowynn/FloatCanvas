# 外部覆盖、输入交接与桌面回退

本文说明浮绘当前外部覆盖后端的设计与复用方法。全文按通用问题组织，不以某个按键或具体应用作为兼容条件。

全屏增强使用 Windows 私有接口，属于有支持边界的工程实现，不是拥有长期兼容保证的公共 SDK。是否启用由本次实际接口初始化决定，不仅凭 Windows 版本号判断；既有实机验证环境为 build 26300，不代表其他环境已通过验收。普通桌面后端不依赖该私有接口。界面、绘图、文档和存储继续使用浮绘原有实现，不把整套 WPF 界面逐帧截图后送入其他进程。

## 1. 将三件事分开验证

1. **显示顺序**：窗口能够位于目标内容上方。
2. **输入归属**：编辑时键鼠进入覆盖层，下层不同时操作；退出后恢复。
3. **呈现路径**：目标是否保留其实际全屏呈现方式，是否最小化或失去前台。

窗口可见、置顶、DXGI 全屏标志和实际输入接管不是同一个证据。不能用其中一项通过来代替另外两项，也不能承诺所有传统独占呈现路径都支持纯外部覆盖。

本文的“普通桌面模式”使用常规窗口与原有桌面输入路径，允许正常的前台切换。它保留基础绘画能力，但不保证覆盖受限的全屏呈现方式。

## 2. 模块与责任

| 模块 | 责任 |
| --- | --- |
| `src/FloatCanvas.SystemOverlay.Native/SystemOverlay.cpp` | 创建系统窗口、持有输入对象、等待触发按键释放、申请和释放委托、处理异步确认 |
| `src/FloatCanvas.Windows/SystemOverlayInput.cs` | 管理原生生命周期和状态，将失败 HRESULT 标识为增强接口异常 |
| `src/FloatCanvas.Windows/OverlayHost.SystemInput.cs` | 把增强输入接入既有画布窗口；确认后才显示输入窗口 |
| `src/FloatCanvas.App/OverlayBackendProtection.cs` | 独立启动探测、持久故障标记、选择桌面后端、显式重新探测 |
| `src/FloatCanvas.App/OverlayPopup.cs` | 直接承载真实 WPF 弹出内容，管理所有权、层级、焦点和关闭 |
| `src/FloatCanvas.App/DesktopSession.OverlayProtection.cs` | 运行中回退时保留文档、资源、文件绑定和撤销记录 |
| `EditorController`、`EditorSession`、渲染与存储模块 | 保持绘图和文档语义，不感知私有接口槽位 |

不要把接口标识、方法位置和模式值散落到工具按钮、文字控件或文档代码中。

## 3. 启动保护：先保证桌面功能可用

设置中的全屏覆盖模式保存为当前配置的 `OverlayMode`（`auto`／`enhanced`／`desktop`），旧配置默认 `auto`，保存后重启生效。强制增强直接初始化，不探测、不自动回退、不启用输入看门狗，失败直接报告；强制普通不加载增强后端。`--desktop-mode` 优先覆盖保存值，`--retry-fullscreen` 临时选择自动模式，均不改保存的选项。

自动模式按以下顺序选择后端：

1. 若指定 `--desktop-mode`，直接使用桌面后端，不加载或探测增强 DLL。
2. 历史异常记录只用于诊断，不阻止本次重新探测。
3. 尝试写入当前配置目录的 `overlay-backend-state.json` 活动记录；写入失败只记警告，不作为能力不足的依据。
4. 启动同目录的独立程序进程，执行内部探测入口。它只创建隐藏的自身窗口并初始化、释放接口，不申请用户输入，不显示界面。
5. 本次探测明确返回接口初始化失败或异常退出时，使用桌面后端。探测超时或子进程无法启动只表示结果不确定，继续尝试实际初始化；超时只结束本次创建的探测进程。
6. 探测成功后，主程序尝试初始化增强后端。窗口重建作为事务执行：失败时保留原桌面窗口并清除失效的增强引用。
7. 正常退出时，只有在界面和原生输入所有者都成功释放后，才清除活动记录。失败记录保留供排查，但下一次启动仍重新验证能力。

独立探测降低首次加载未知 ABI 对主程序的影响，但不证明主进程之后每次调用都不会崩溃。本实现优先避免把支持的环境误判为不支持；因此结果不确定时仍尝试实际初始化，代价是这种情况下的原生卡死或崩溃仍可能影响主进程。

### 用户恢复入口

先退出同一配置的浮绘实例，再运行：

```powershell
FloatCanvas.exe --desktop-mode
FloatCanvas.exe --retry-fullscreen
```

前者强制桌面模式，也用于强制增强失败后的设置恢复；后者为兼容旧命令保留，临时选择自动检测。两个参数不能同时使用。配置目录仍遵循既有 `--profile` 参数，不迁移或清空画布数据。自动增强会话的托盘还提供“改用普通桌面模式”。

普通启动对历史画布的处理不变。若原生故障造成程序异常结束，下一次启动重新验证增强接口；可使用既有历史画布恢复功能找回已写入的恢复数据。

## 4. 输入委托：显示与前台不必绑定

当前原生后端使用：

```text
自有隐藏系统窗口
  → InputSite
  → WindowsMessageDelivery
  → InputDelegationInputObject
  → 订阅委托变化
  → 等待进入动作释放
  → 请求委托
  → 检查代次、目标进程与启用确认
  → 在自身 UI 线程恢复局部焦点
  → 显示编辑界面
```

这些类型属于 `Windows.UI.Internal.Input`。接口标识和方法位置集中在原生模块，不能把它们当成公开、稳定的 WinRT 合同。

当前申请／释放模式为 `0x2E / 0x21`，来自已经观察并验证的系统调用组合。各独立位的语义没有全部确认，不应自行拆位命名或推广到其他构建。窗口使用 band 16 也只说明系统层级，不能单独证明传统独占呈现兼容。

每次进入都有代次编号。迟到确认不能恢复已退出的旧会话；目标发生变化时取消等待。申请尚未得到确认时，不能声称已接管输入。

## 5. 解决进入时按键尚未释放的问题

问题是输入归属改变的时机：下层已经收到了某个按下事件，但相应松开事件被新覆盖层截获，下层就可能保留按下状态。

实现不针对单个修饰键，也不通过向下层补发某个松键事件修补状态。

- 外部进入请求先返回消息循环，不在快捷键通知栈内立即接管。
- 随后检查仍按下的键盘按键与鼠标按钮，结合异步状态和当前线程消息队列状态。
- 仍有按下状态时继续等待；目标切换或用户取消时释放等待。
- 全部释放后申请系统输入委托，收到有效确认后才显示编辑界面。
- 等待期间继续显示穿透头像；工具条实际显示时再隐藏头像。

[GetAsyncKeyState](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-getasynckeystate) 在权限隔离等条件下可能返回零，不能把零一律当成物理松开。[GetKeyState](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-getkeystate) 又随线程读取键盘消息而更新，因此要同时考虑消息循环边界。

当前代码检查虚拟键的按下位，不使用不可靠的“自上次查询后是否按过”低位。这里的检查范围包括普通按键和鼠标按钮，并非仅检查修饰键。

## 6. 真实 WPF 界面、菜单和输入法

### 窗口与弹出层

保留真实 WPF 控件及其事件、布局与文本能力。主工具条、画布输入窗口和弹出内容分别承载，不把工具条移动变成全屏画布重绘。

WPF 默认 Popup 会创建独立 HWND，它未必具有覆盖层需要的所有权与层级。因此使用统一的弹出承载器：

- 用自有 HwndSource 的 RootVisual 承载真实菜单、下拉框和提示内容；
- 使用一致的所有者、局部焦点和关闭规则；
- 阴影及留白放入布局根内部，保证客户端尺寸包含完整气泡；
- 普通桌面模式恢复使用 WPF 原有弹出路径。

“UI 是自己绘制的”不等于所有默认弹出 HWND 都处于正确层级。必须验证菜单和子菜单本身。

### 非文本焦点与输入法

输入归属、WPF 键盘焦点、TSF 文本文档焦点是不同状态。只清除 WPF 焦点，可能仍留下之前的文本上下文。

- 真实文字编辑保留输入法能力。
- 数值控件按其用途限制输入法。
- 点击面板空白时，把焦点移到明确的非文本命令表面。
- 原生画布没有文本存储，使用当前线程的空文档上下文结束之前的文本焦点。
- 不切换用户的全局输入语言，不通过全局禁用中文输入掩盖焦点错误。

[WPF 与 Win32 互操作说明](https://learn.microsoft.com/dotnet/desktop/wpf/advanced/wpf-and-win32-interoperation) 可用于理解 HWND、HwndSource 和焦点边界；它不为本文使用的私有覆盖接口提供兼容保证。

## 7. 系统文件框：主动交接输入

系统打开／保存框按普通系统窗口处理：

1. 保留用户的编辑意图与会话代次。
2. 暂停增强输入委托，并隐藏画布输入窗口。
3. 让系统文件框正常激活和接收输入。
4. 返回后，以当时真实的前台窗口重新申请输入。
5. 显式退出、关闭或过期会话不再恢复；嵌套和异常路径也必须对称结束。

系统文件框可能改变下层全屏应用的呈现方式；本阶段不通过抢前台或拦截激活强行维持它。关键要求是文件操作正常，并且关闭文件框不会意外结束浮绘编辑。

## 8. 运行中回退：释放后重建承载

自动模式中增强接口发生可恢复故障，或用户主动选择桌面模式时：

1. 本次会话禁用增强能力并保留故障标记，禁止自动反复重试。
2. 从原生回调返回后，再进入 UI 调度器执行恢复。
3. 先结束增强输入会话。无法确认释放成功时停止热切换，不能再启动另一套接管逻辑。
4. 等正在进行的文档操作完成，提交文本与参数，尝试写入恢复数据。
5. 保留同一份 EditorSession 和 AssetLibrary，记录当前文档、文件绑定、工作区历史及待处理打开请求。
6. 释放旧窗口、事件订阅和输入后端，再创建普通桌面界面。
7. 重新绑定原文档，因此撤销／重做仍有效。回退后先保持穿透，用户可正常进入桌面编辑。

如果恢复文件暂时无法写入，仍以内存中的同一对象图完成受控切换，不用空白文档替换它。若无法安全释放，或重建失败，报告限制并保留故障标记，以便退出后从桌面入口恢复。

### 不能用 try/catch 保证的情况

错误 HRESULT、入口缺失等可以受控处理。原生访问违规、内存破坏或卡死不能保证在同一进程里无损恢复。当前隔离的是启动探测，不是把全部运行时 WPF 与原生调用移到独立进程。

因此保证边界是：基础桌面路径不依赖这组增强接口；可恢复失败执行安全回退；历史异常不推导为当前不支持。不能将其描述为“任何底层故障都不会影响当前进程”或“任何环境都不会误判”。

### 输入租约独立看门狗

本节的看门狗只用于自动模式。强制增强不创建监测线程、不注册心跳计时器，也不执行本节的紧急组合键及超时终止保护。

增强后端向外部前台申请输入时启动独立原生线程。这是运行中的输入故障保护，不是系统能力检测。线程每约 100ms 向拥有者 HWND 投递专用心跳消息，收到后更新响应时间；原生计时器也可报告进展。不能只依赖 `WM_TIMER`：它优先级低，在持续普通消息下可能长期不生成，不能据此把繁忙界面判为卡死。隐藏窗口回归已复现旧机制在持续处理消息时被误杀，并验证专用消息下仍能响应。

连续 5 秒工作时间无法响应心跳时，看门狗终止浮绘自身进程，由 Windows 撤销该进程的输入租约；不会从错误线程调用 STA COM，也不会向其他应用重放按键。计时使用 `QueryUnbiasedInterruptTime` 排除睡眠和休眠时间。真正长时间阻塞的 UI 仍可能触发保护；此机制不能证明阻塞一定是死锁。5 秒不是正常交互延迟目标。参考：[WM_TIMER 优先级](https://learn.microsoft.com/windows/win32/winmsg/wm-timer)、[工作时间计时](https://learn.microsoft.com/windows/win32/api/realtimeapiset/nf-realtimeapiset-queryunbiasedinterrupttime)。

持有委托期间，`Ctrl+Alt+Shift+F12` 由看门狗直接观察，不注册全局热键。它先请求拥有者正常释放，750ms 后仍未释放则终止自身进程。原生释放失败同样进入有界终止。权限或安全桌面可能限制异步键状态读取，因此自动心跳超时与紧急键互为补充。正常结束租约立即撤销看门狗，不影响穿透状态。

强制终止不能保存尚未进入恢复快照的修改。已有 `overlay-backend-state.json` 保留，后续启动仍重新检查能力；当前配置目录的 `overlay-input-safety.log` 记录原因、时间、退出码、进程和拥有者线程、心跳年龄、投递次数、响应次数及投递错误。旧日志缺少这些字段，无法倒推出过去某次超时的准确阻塞点。日志写入最多等待 50ms，磁盘故障不得阻止输入退让。隔离子进程测试验证真实 watchdog 线程终止与时限；真实增强委托、实际输入去向及各设备恢复时长仍需单独验收。

## 9. 构建与验证

```powershell
dotnet build tests/FloatCanvas.AppTests/FloatCanvas.AppTests.csproj -c Release
dotnet tests/FloatCanvas.AppTests/bin/Release/net10.0-windows/FloatCanvas.AppTests.dll --overlay-protection-only
dotnet tests/FloatCanvas.AppTests/bin/Release/net10.0-windows/FloatCanvas.AppTests.dll --overlay-protection-runtime
```

第一组验证命令参数、持久标记、初始化失败、显式重试、探测进程退出与超时。第二组在隐藏的自有窗口中验证实际初始化回滚和界面承载替换，检查文档、资源、文件绑定、撤销／重做以及前台保持；它不替代全屏应用中的真实硬件输入验收。

启动级验证应至少覆盖：没有增强 DLL 的显式桌面启动、没有增强 DLL 的自动回退、正常增强启动、上次未正常退出，以及显式重新探测。验证实际运行的主进程是否加载了增强 DLL，不能只依据设置或返回值。

发布前还应按目标环境验证：绘画、工具快捷键、菜单与子菜单、中文输入、进出编辑、退出恢复、跨应用笔迹、系统文件操作、DPI 与颜色。Raw Input、DirectInput、进入前长按和异常退出的组合要分别记录，不能复用其他机制的通过结果。

## 10. 当前交付边界

已验收的基础覆盖功能与完整界面接入保留。严格绘画性能非回退、实际显示帧率及尚未覆盖的完整测试组合，按用户决定留待后续优化。

已有同几何受控采样为 240 次移动、241 个笔迹点／提交帧、零 WPF 布局；候选队列到提交 P95 为 18.27ms，旧桌面基线为 9.82ms。它满足 33ms 管线目标，但未证明性能不退步，也不是物理输入到显示器的延迟或真实显示 FPS。本次保护层不重新开启性能专项。

历史实验和诊断流水保存在独立归档中；本页只保留最终架构、可复用机制、操作方法与已知限制。提交与发布状态以仓库记录为准，本文不代表正式发布。
