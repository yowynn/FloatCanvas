# Windows 系统截图与增强画布交接

三期要求包含两个独立结果：截图快照仍是工具条覆盖蓝色画布的原画面；系统选区和操作界面能够覆盖画布。隐藏工具条或只验证普通 topmost 窗口都不足以证明修复。

## 已确认的机制

本机窗口事件实测：增强显示与 WPF 工具位于 band 16，Windows 截图的 `SnipOverlayRootWindow` 和全屏 `XamlWindow` 位于 band 1。对普通置顶窗口执行前后排序不能改变两者的 band。新建隐藏窗口实验中，`SetWindowBand` 返回错误 5；改 WPF owner 也不改变其 band。产品没有提权或修改系统配置来绕过限制。

增强输入委托下，系统截图已显示，全局前台 HWND 仍可留在原接收器。初版检测只检查全局前台，因此完全漏掉截图，编辑租约继续存在。后来逐消息时序证实 UI 线程正常处理消息，排除了先前“线程停住”的猜测。检测必须同时检查实际可见的系统截图窗口。

## 实现

`OverlayHost` 识别当前支持的系统截图窗口类、截图进程、全屏覆盖范围及 topmost 状态；普通截图工具编辑窗口不触发。先将最后呈现的画布像素与应用提供的 WPF 工具图像按原 z-order 合成到临时普通桌面窗口，再隐藏增强显示和这些工具的原生窗口，释放编辑输入。即使全局前台不变，系统截图也能取得输入。

临时窗口没有输入行为，不激活前台，只放在系统截图窗口后。它保存交接前的画面，避免取消手势、关闭工具和异步预览完成改变截图内容。系统截图结束后清理临时窗口，恢复实时显示，只恢复应用仍认为可见的工具；退出编辑而关闭的工具不会重新弹出。浮动头像的刷新在截图期间暂停，结束后恢复，避免新建 band 16 头像再次遮盖截图。快照分配失败也必须释放编辑输入。

普通模式的原有窗口排序不受该机制接管。它也不修改热键、不替换图片资源、不写画布文档，且不承诺其他截图程序均已验证。

## 验证

`FloatCanvas.AppTests --phase3-system-screenshot-only` 使用两个桌面之外的自有显示／工具 HWND，分别验证真实 band 16 和 band 1、WPF 工具合成像素、后来置顶 peer 的实际 z-order、冻结画面不被后续渲染改变、输入释放、窗口销毁与恢复、工具逻辑可见状态、头像抑制及失败清理。测试不取得真实编辑租约，覆盖的是生产会话策略与原生呈现；前台事件检查为 0。

`--phase3-screenclip-observe` 是 60 秒有界的只读窗口事件观测；`--phase3-window-band-inventory` 只读取指定程序的窗口类、band、可见性、owner 和边界。它们不读取窗口正文、不捕获桌面图像，也不注入输入。

桌面回归使用隔离接收器和真实 Debug `DesktopSession`。修复前的探针记录了“截图全屏窗口出现，但编辑与增强显示仍存在”；修复后的记录确认全局前台未切换时仍进入交接，WPF 工具捕获约 12.7 ms，随后编辑输入及增强显示均释放。实际图像中，蓝色画布与完整工具条同时被系统蒙层遮罩，工具条不再被蓝色实时显示盖住。

另用正式 Debug 主程序 `0.2.1+bc4a473`、独立 profile 和自有蓝框文档复验：进入编辑后工具条在蓝框上方；系统截图出现时，两者同时被蒙层遮罩，系统截图快捷按钮清晰显示在蓝框上方。只读窗口记录同时确认该实例的 band 16 显示和工具均隐藏，band 1 临时呈现位于真实 `SnipOverlayRootWindow`／`XamlWindow` 后。终止本次测试新建的截图宿主后，冻结工具条消失、实时蓝框恢复，随后可重新进入编辑。这是正式应用的呈现和恢复检查；没有完成选区拖动或读取最终保存的系统截图，不能把它扩写为这些步骤已通过。

此机器的 PrintScreen 绑定到 ShareX，不能当作 Windows 截图回归。系统回归使用本机已有的 `ms-screenclip:` 调试入口；产品本身没有调用该入口。它只证明本机系统截图呈现，不能冒充物理 Win+Shift+S 按键测试。键盘状态回归另行覆盖左右 Win+Shift+S 的完整边沿下放。微软正式应用集成使用[新版截图协议](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-snipping-tool)；此测试不新增该集成功能。

自动化工具未枚举系统截图覆盖窗口，选区拖动被其目标窗口检查拒绝。当时未取得选框／快捷按钮的直接鼠标交互证据，因此没有将这部分自动化检查写为通过。验证取消时不能只向接收器发送 Escape 并假定截图已结束；需回读窗口可见性。测试结束时已清理自行启动的截图宿主进程，保留原截图工具主窗口和原浮绘运行实例。

## 人工验收（2026-10-25）

用户回传实际截图，并确认“看起来这个截图效果已经符合预期了”。结果图显示完整工具条及“线条与箭头”配置窗口位于红色画布前方，没有被画布覆盖或从截图中消失。结合用户现场反馈，本机系统截图问题记为人工验收通过；原图和结论归档到三期 Notion 任务。

该验收补足此前的设备确认，不改写上述自动化未直接执行系统选区操作的事实，也不扩展为其他截图程序或操作系统版本的验收。

## ShareX 选区交接（2026-10-28，初次适配）

用户报告 ShareX 区域截图时，选区界面与浮绘 UI 仍被实时画布覆盖。原检测同时限定 Windows 截图进程和窗口类，ShareX 不会进入已有交接路径。现将 ShareX 的可见、覆盖至少一个绘图屏幕、置顶、无标题栏且无可调整边框的 WinForms 窗口接入同一机制；截图结束判断同样使用扩展后的规则。普通设置和非全屏编辑窗口不触发。ShareX 的全屏编辑器和选区使用同一种表面，两者均允许覆盖增强画布，不依赖本地化标题。规则依据 [ShareX 21.0.0 RegionCaptureForm](https://github.com/ShareX/ShareX/blob/v21.0.0/ShareX.ScreenCaptureLib/Forms/RegionCaptureForm.cs)。这是一条内置程序兼容规则，没有增加用户白名单设置，也不代表未知截图软件均已兼容。

回归入口为 `FloatCanvas.AppTests --isolated-ui-desktop --third-party-screenshot-only`。它在独立、不切换到前台的桌面上启动名为 ShareX 的自有 WinForms 子进程，窗口使用屏幕外的合成场景，不启动用户的 ShareX、不采集桌面、不发送键鼠输入、不取得真实编辑租约。同一最终夹具使用 `6971da9` 的 Windows 程序集时，在“ShareX region UI triggers production handoff and hides the enhanced canvas”处失败；使用修复版时 24 项检查通过。检查包括自动识别、band 16 隐藏、band 1 临时呈现和真实 WPF 工具像素、对端层级、持续交接、关闭后的恢复，以及普通 ShareX 窗口和未知程序不触发。中文标题与全屏编辑器也有检测检查。测试子进程在报告就绪前校验原生置顶标志，避免 WinForms 延迟应用属性造成夹具时序差异。

Release 解决方案构建为 0 警告、0 错误；Windows 截图原有专项 16 项、Windows 默认回归 1129 项、原生窗口排序 58 项均通过。应用按已有 `--isolated-ui-desktop --background-regression` 入口通过 8094 项检查，依赖当前输入桌面的头像捕获及桌面合成提示检查按该入口的既有规则跳过；不带后台参数的首次隔离运行在头像鼠标捕获断言处失败，未将其写为完整通过。日志和基线差分构建保存在 `.artifacts/sharex-handoff-20261028/`。

这些检查证明窗口特征与生产交接路径的兼容，不替代当前桌面上真实 ShareX 的区域拖动及最终图片验收，也不证明抓图前通知时序或其他 ShareX 版本、窗口框架的兼容。用户正在运行的实例未替换或重启。

## 通用临时界面交接与自身窗口排序（2026-10-28，通用识别试验已撤回）

用户进一步报告未告知名称的截图工具仍会遮挡。第一轮只读观测未读取该程序名、窗口标题或屏幕像素：外部全屏置顶窗口处于 band 1，FloatCanvas 的实时显示处于 band 16，真实工具条及面板已隐藏，头像仍可见。该记录未从转换前开始采样，因此不能确定隐藏与抓图的精确先后；它证明遮挡期间并不存在一扇仍可见却排到画布下方的真实工具条。用户确认截图工具会冻结画面，结合层级记录，故障机制是实时高层画布继续覆盖外部冻结画面，也覆盖该画面中的工具条像素；冻结瞬间的画面本身可以是正确的。第二轮观测在用户操作完成前已超时，没有捕获该次转换，不作为验证证据。原始记录留在 `.artifacts/window-order-observe-20261028/`，未在此记录外部软件名。

试验曾将可见窗口路径改为按行为判断：外部窗口覆盖至少一个绘图屏幕、可见、置顶、无标题栏且无可调整边框，不标为 `WS_EX_APPWINDOW` 或 `WS_EX_TRANSPARENT`，且为 `WS_EX_TOOLWINDOW` 或有 owner。匹配后复用整体冻结呈现、隐藏增强窗口、释放编辑输入和结束恢复机制；持续交接与结束检测使用同一条件。该试验路径不读取进程名、不依赖窗口类或标题，暂时移除了 ShareX 专用分支，并保留 Windows 截图的提前交接适配。窗口样式含义见 [Microsoft Extended Window Styles](https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles)。这些属性并非操作系统提供的“正在截图”语义标记。用户后续实测该试验仍不能解决陌生截图工具的问题，当前已撤回通用识别，最终范围见下节。

同时补充独立排序约束：只要可见的自身工具、弹窗或输入 HWND 落到同 band 的画布下方，窗口排序检查就恢复 UI 在前、画布在后的顺序，保留 UI 原有相对顺序和既有外部置顶 peer。自身 SHOW／REORDER 事件也请求检查。原实现的提前返回只检查丢失置顶标志或外部普通窗口挡住画布，遗漏了自身顺序倒置。修复前，`FloatCanvas.WindowsTests --window-order-native` 在新增的“Own tool/canvas inversions recover independently of screenshot detection or external blockers”检查失败；修复后通过。此处故障注入只改动自有测试 HWND，不能冒充已经找到用户现场的原始改序调用；现场记录的真实工具条隐藏与这个独立缺口应分别理解。

`FloatCanvas.AppTests --isolated-ui-desktop --generic-screenshot-only` 使用任意进程名和标题的外部子进程驱动生产路径，修复前在“UnlistedCapture region UI triggers production handoff and hides the enhanced canvas”失败，修复后通过。覆盖 WinForms／WPF、无 owner 工具窗口及有 owner 的辅助窗口，以及普通全屏主窗口、无 `WS_EX_APPWINDOW` 的普通无 owner 主窗口、鼠标穿透界面、不置顶、小窗口、有边框窗口等排除条件。窗口排序回归另覆盖 UI 与画布倒置恢复、不争抢外部置顶界面、无激活、焦点／捕获保留、隐藏／截图期间暂停及事件稳定后不持续改序。

本轮没有替换或重启当前实例，也没有取得陌生截图软件在新构建上的实际选区、成图验收。行为匹配、独立窗口排序、第一轮现场故障观测及新构建实机验收的证据边界分别保留。

试验阶段验证结果：Release 解决方案构建 0 警告／0 错误；任意程序名截图专项 28 项、ShareX 兼容专项 28 项、Windows 截图原有专项 16 项、Windows 默认回归 1129 项、原生窗口排序 61 项及应用后台回归 8094 项均通过。后台应用回归仍按其既有入口跳过依赖输入桌面的头像捕获和桌面合成提示检查。这些模拟窗口检查未覆盖用户的陌生截图工具，不能替代用户后续报告的失败结果。试验日志及隔离构建保存在 `.artifacts/window-order-general-20261028/`。

## 最终收口（2026-10-28，当前实现）

用户实测陌生截图工具仍存在遮挡，但在选区出现、画面冻结后使用已配置的画布显隐快捷键隐藏实时画布，可以继续操作截图而不中断。该结果进一步支持实时画布覆盖冻结画面的机制，但不说明可以通过通用窗口样式可靠判断所有工具的截图生命周期。当前自动交接范围恢复为 Windows 系统截图与 ShareX 两个产品；恢复 ShareX 的进程／WinForms 窗口特征判断，通用行为匹配和对应的肯定识别测试入口已移除。新增未知程序即使拥有同样全屏置顶窗口也不自动接管的回归，保留已有自身窗口排序修复及原生回归。

其他会先冻结画面的工具可采用用户已验证的手动流程：先启动截图并等选区出现，再隐藏实时画布；完成或取消截图后手动恢复显示。此次不再扩大自动识别条件，也不增加新的快捷键或设置项。当前不将通用自动兼容作为已完成能力。

收口后 Release 解决方案构建 0 警告／0 错误；ShareX 专项 26 项（含未知同形窗口不接管）、Windows 截图专项 16 项、原生窗口排序 61 项及 Windows 默认回归 1129 项均通过，证据位于 `.artifacts/screenshot-scoped-final-20261028/`。自身排序代码与已通过 8094 项后台应用回归的版本一致；本次缩小自动识别范围后采用上述定向检查，未重复声明一次新的完整应用回归。验证期间未替换或重启用户实例。
